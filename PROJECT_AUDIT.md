## Architecture as inspected

Static multi-page HTML; each page loads Tailwind from `cdn.tailwindcss.com` and repeats an inline configuration, plus Google Fonts (Inter and JetBrains Mono), shared [style.css](assets/css/style.css) and shared vanilla [main.js](assets/js/main.js). There is no React, TypeScript, compiled Tailwind, package manifest, lockfile, bundler, server runtime or deploy configuration. README's local workflow is open the file or serve static files with Python. Its claim of a complete reproduction conflicts with the supplied production inventory; the claimed filter labels and homepage lab grid are also unreliable as an inventory.

No application API route or API client, fetch-based submit, DB client, Supabase project config, migrations, Edge Functions, Auth, Storage, queue, Turnstile or keep-alive implementation exists in the checkout. The only observed local persistence is `br_cookie_consent`. External resources are font and Tailwind assets, plus support mail links; assets aren't application APIs. No test suite, Docker setup, workflow config or monitoring integration is checked in. The BRD/FRD describe a single Vercel serverless lead endpoint backed by private Supabase storage; they do not supply a verified endpoint path, payload keys, schema or credentials. Do not guess them.

Four distinct form templates appear on **five pages** (Home and Students duplicate waitlist). Each handler cancels the submit, displays a local toast and resets the form. Native HTML required/email checks provide partial UX; there is no backend confirmation, attribution, retry state, request lock, data storage or delivery. “Added to the waitlist”, “Inquiry Received” and “Message Sent” are false confirmations. Waitlist name and company input are interpolated into toast `innerHTML`, an unsafe DOM injection path. Without handlers, default form behaviour is unsuitable for personal data; named inputs on forms without an explicit method may appear in a GET URL. Do not preserve either behaviour.
